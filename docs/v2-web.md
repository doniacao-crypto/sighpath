# SightPath v2 — the browser measurement app

- Status: Shipped in `web/`
- Date: 2026-11-15 (v2), updated 2026-11-22 (v3, feature parity with the desktop app)
- Owner: Huilin

## What v2 is

SightPath v2 is the **measurement app in the browser**. The camera, the
calibration and the pursuit test all run inside the page — no install, no
desktop app, and no server between the lens and the metric. It is a standalone
Next.js 15 application in `web/`, and it computes **the same measurements** as
the desktop app: tracking ratio, direction match, speed match, pursuit gain,
accuracy in degrees of visual angle, and phase lag.

What moved to the browser was scoped by what has to sit next to the camera. ADR
0001 split the codebase on a latency line — tracking, calibration and filtering
run next to the lens (a saccade completes in 30–80 ms, so a frame round-trip to
a server cannot measure one), while records, reports and normative comparison
are server work. v2 is the client half of that decision, built and running:
backlog item **A-15**.

v2 measures; it does not manage patients. The Clinical Lead still interprets
every number it produces (ADR 0003), and the thresholds it shows are the same
provisional ones the desktop app shows.

**v3 brings the browser version to feature parity with the desktop app.** The
saccade protocol, the fixation stability measurement and the fixed-head grid
validation were ported with the same parity contract as the pursuit test, so the
browser runs the same four protocols the desktop app runs:

| Protocol           | What it measures                                   | Port                |
| ------------------ | -------------------------------------------------- | ------------------- |
| Smooth pursuit     | Gain, RMS error, direction and speed match         | `lib/metrics.ts`    |
| Saccade            | Latency, direction error, anticipatory and express | `lib/saccade.ts`    |
| Fixation stability | BCEA, microsaccade rate, stability                 | `lib/fixation.ts`   |
| Grid validation    | Accuracy in degrees against known angles (A-4b)    | `lib/validation.ts` |

The report can be printed or saved as a PDF from the browser, the trajectory, the
position-over-time plot and the gaze heatmap are drawn on a canvas and exported as
PNG, the tracked landmarks are shown over the preview, and two stored runs of the
same protocol can be compared.

## The parity contract

Two implementations of one measurement stay honest only if something makes them
compare. That something is the parity fixtures:

| File                                          | What it covers                                 |
| --------------------------------------------- | ---------------------------------------------- |
| `web/tests/fixtures/parity-faithful.json`     | A tracker that follows the target              |
| `web/tests/fixtures/parity-damped.json`       | A tracker that lags behind the target          |
| `web/tests/fixtures/parity-noisy.json`        | A noisy tracker                                |
| `web/tests/fixtures/parity-head-drift.json`   | A run with a moving head                       |
| `web/tests/fixtures/parity-saccade-*.json`    | Saccade trials, pro and anti-saccade           |
| `web/tests/fixtures/parity-fixation-*.json`   | A steady fixation, microsaccades, an excursion |
| `web/tests/fixtures/parity-validation-*.json` | A healthy grid, an outlier, a missing point    |
| `web/tests/fixtures/parity-trajectory.json`   | The path, the time series, the density grid    |

Each fixture holds a deterministic synthetic frame set **and** the metrics the
**Python** implementation produced for it — generated by running the desktop
code in `src/smooth_pursuit_test.py` and `src/metrics.py`. The TypeScript tests
in `web/tests/parity.test.ts` feed those same frames to the port in
`web/lib/metrics.ts` and assert the same numbers, to the precision the fixtures
carry.

The contract is one sentence: **the two versions cannot drift apart silently.**
Change what the Python code measures and the TypeScript test fails until the
fixtures are regenerated and the port is updated; change the port and the same
test fails. Regenerating them is `python tools/generate_parity_fixtures.py` —
the generator lives at the repository root, not in the web app.

Every protocol is held to the same contract: `tools/generate_parity_saccade.py`,
`tools/generate_parity_fixation.py`, `tools/generate_parity_validation.py` and
`tools/generate_parity_trajectory.py` run the **desktop** implementation over
deterministic inputs and write the fixtures the TypeScript tests assert against.

The calibration model is held to the same contract. `web/lib/ridge.ts` and
`web/lib/features.ts` port the Ridge fit and the polynomial features of
`src/gaze_estimator.py`, and `web/tests/calibration.test.ts` asserts the fitted
model, its predictions, the leave-one-point-out error and the head-pose spread
against the Python behaviour.

## What deliberately stays in v1

| Stays in the desktop app (v1) | Why it does not move yet                                     |
| ----------------------------- | ------------------------------------------------------------ |
| Patient records               | Hosted PHI needs the ADR 0005 design first (A-17)            |
| The PHI encryption key        | It stays in the OS keychain on the clinic machine            |
| Accounts and admin roles      | Access control and audit come with the hosted design         |
| The PDF report                | A report is part of the clinical record, not the measurement |
| The validation test           | It is the ground-truth harness (A-4b, A-5)                   |

The reason is ADR 0005's hard gate: **no real patient data touches a server
until the target regime's non-negotiables are designed in.** Hosted PHI needs
encryption at rest and in transit, key management that is not tied to a single
OS keychain, per-user access control with a full audit trail, region-partitioned
data residency, lawful basis and explicit consent, a retention and deletion
policy, breach notification, and BAAs for US clinics. That work is still open —
**A-14**, **A-16**, **A-17** and **A-18** in `docs/BACKLOG.md`.

A browser app must not hold clinical data before that work is done, so v2 holds
no clinical data at all: no server, no database, no account, and nothing
persisted beyond the tab it runs in.

## Deployment on Vercel

`web/` is a standalone Next.js app — the repository root is not part of its
build.

- Point the Vercel project at the repository and set **Root Directory** to
  `web`.
- **No environment variables are needed.** There is no server-side storage, no
  API key and no database; the pages are rendered, but nothing is stored.
- The face landmarker model and the MediaPipe wasm are served from
  `web/public/`, so they ship with the deployment — nothing is fetched from a
  third party at runtime.
- The camera needs a secure context: `https`, or `http://localhost` in
  development. Vercel serves https, so nothing else is required.
- `web/next.config.ts` sets the cross-origin isolation headers (COOP/COEP) the
  threaded MediaPipe wasm build needs; Vercel passes them through unchanged.
- Build with Node 22 — the same version the `web` CI job uses.

## Known limits

- **The gaze estimate is damped.** The tracker lags the eye, so pursuit gain is
  under-reported. That is the same measurement problem the desktop app has, and
  the reason the accuracy work (**A-3**, **A-4a**, **A-4b**) is still open. The
  port neither caused it nor can fix it.
- **The thresholds are not clinically validated.** v2 shows the same provisional
  thresholds as v1; the sign-off register is still open (**A-6**, ADR 0002).
- **There is no ground truth in the browser yet.** v2 has parity with the
  desktop app, and the desktop app has not been validated against a ground
  truth (**A-4a**, **A-4b**, **A-5**). Parity with an unvalidated measurement is
  not validation.
- **Unpinned hardware.** The browser runs on whatever camera and lighting the
  machine has; the pilot hardware floor (**A-13**) is not enforced in the
  client.

## Roadmap — what a v3 would need

1. **Ground truth in the browser.** Port the fixed-head grid test (**A-4b**) so
   the browser build can be measured against known angles, and compare it
   against the Clinical Lead's reference tracker once that device is repaired
   (**A-4a**).
2. **Hosted session storage, behind the ADR 0005 design.** A v3 that keeps
   results needs the region-partitioned, compliance-first backend described in
   ADR 0005 and backlog **A-14**, **A-16** and **A-17**: per-user access
   control, audit trail, residency, consent, retention and deletion. Until that
   design is written down and reviewed, a v3 stays measurement-only.
3. **Patient records and accounts, properly.** The browser version still holds
   no clinical data. The desktop app keeps the patient records, the accounts and
   the reports; moving them to a hosted service needs the ADR 0005 design
   (encryption at rest and in transit, key management, per-user access control
   with an audit trail, residency, consent, retention and deletion), and the
   browser app would need the same guarantees before it may hold anything of a
   patient's.
